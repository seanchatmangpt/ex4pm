## 1. Summary

The user's direction this turn: beam4pm should emit a real OpenAPI spec, and its
`json_api` exposure (AshJsonApi routes) should be generated by `ggen_igniter` from
ontology admission facts, following the same pattern beam4pm already uses to
manufacture `lib/beam4pm_ash_domain.ex` and `lib/beam4pm_ash/resources/*.ex` from the
admitted `bpm:RecordType` graph.

Four research passes this session establish the real ground this plan stands on:

1. **beam4pm's merge blocker is RESOLVED, not open.** `~/ex4pm/CLAUDE.md`'s standing
   note ("beam4pm is BLOCKED (external), in-progress uncommitted merge") is **stale**.
   beam4pm's working tree is clean, `HEAD` is `61f8d48 merge: integrate
   local/session-integration (11 real branches' work)`, no `.git/MERGE_HEAD` exists.
   beam4pm edits become possible **pending explicit user confirmation** — this plan
   does not perform any, per the user's own framing this turn ("plan only, no beam4pm
   edits this turn").
2. **`ash_json_api` is a real dependency in beam4pm's `mix.lock`** (`1.7.1`, plus its
   own dep `open_api_spex 3.22.4`) but is **not wired to anything** — zero resources
   declare a `json_api do ... end` block, zero references to `AshJsonApi` in
   `lib/beam4pm_application.ex` or the one router file present
   (`lib/beam4pm_ash/resources/meta_router.ex`), and zero OpenAPI-related files or
   routes anywhere in `lib/` or `priv/`.
3. **`ggen_igniter` has no real AST-level DSL-injection precedent for Ash resources at
   all**, and specifically none for `AshJsonApi`'s `json_api do routes do ... end end`
   block. This is a real gap, not an assumed-available capability — named explicitly
   in §3 below, with the one viable generation strategy the research does support.
4. **`ash_json_api`'s own DSL is compile-time-macro-based**, not data-driven at
   runtime — `get`/`index`/`post` route entries are `Spark.Dsl.Entity` structs
   resolved from literal Elixir source at compile time (verified against the real
   vendored `ash_json_api` v1.7.1 source under `~/xaas/deps/ash_json_api`). There is
   no `routes: [...]` keyword or runtime data list a generator could populate instead
   of emitting literal macro-call text.

Net position: this is executable, using beam4pm's own existing dual-engine
manufacturing pattern and EEx whole-file (or whole-block) templating — not via any
structured AST injection ggen_igniter does not yet have. The concrete gap to close
before beam4pm-side execution is a small, scoped addition to `ggen_igniter`'s
templating surface (or, more precisely, to the `beam4pm-process-model-pack`'s own
templates/queries), not a new ggen_igniter core capability.

Confirmed from `beam4pm-merge-and-ash-state` research, exact file:line evidence:

  bpm:RecordType graph. Do not edit.`

  - **Stage 1a** (`igniter_sync.sh:84-90`): per-resource generation, `--for-each

  (`vendor/ggen-marketplace/packs/beam4pm-process-model-pack/`), not under a local

- beam4pm runs **two parallel manufacturing engines deliberately**: the Rust `ggen`

### 2.3 `ggen_igniter`'s real injection capability (and its limit)

From `ggen-igniter-ash-dsl-gen-precedent` research, confirmed against
`/Users/sac/ggen_igniter`:

- `lib/ggen_igniter/injection.ex` (169 lines) and `lib/ggen_igniter/frontmatter.ex`
  (412 lines) implement the entire `inject`/`before`/`after`/`at_line`/`skip_if`
  surface as **line-text/marker-based splicing** (`resolve_injection!/1` →
  `Actuate.inject_content!/5`, marker is a plain string or compiled `Regex` matched
  against a single line). There is **no AST awareness** of Elixir syntax, and no
  concept of "find the `json_api do ... end` block" or any Spark DSL section
  boundary.
- Real AST/zipper-level Igniter usage exists in this repo (`Igniter.Code.Module`,
  `Igniter.Code.Function`, `Igniter.Code.Common`), but **only** for `mix.exs` deps
  lists (`doctor_fixes.ex:360-361`,
  `mix/tasks/ggen_igniter.install.ex:21-22,194-206,238-239`) and
  `application.ex` supervision-tree patching, and for identifier-rename refactors
  (`refactors/safe_rename.ex:64,102,128`). None touch `Ash.Resource`, `json_api do
  ... end`, or any Spark DSL section.
- The one real, working Ash-generation pack in `ggen_igniter`
  (`test/fixtures/ash-lifecycle-pack/`, documented in
  `docs/integrations/ash/resources.md`) does **whole-file EEx regeneration** of
  `attributes do...end`/`relationships do...end` blocks via `mode: file` templates —
  explicitly **not** surgical injection. Per that doc's §5: "the entire resource
  module is re-rendered" on any attribute change. This pack has no `json_api` section
  anywhere (`grep -rl "json_api" priv/` → nothing).
- `ash_json_api` is **not a dependency of `ggen_igniter` itself** — no `mix.lock`
  entry, no `deps/ash_json_api`. No template or pack in this repo could exercise it
  today even in principle.
- `ash_json_api`'s real DSL shape, read from the vendored `~/xaas/deps/ash_json_api`
  v1.7.1 source (`lib/ash_json_api/resource/resource.ex:82-134`): `get`/`index`/`post`
  route entries are `%Spark.Dsl.Entity{}` structs (`@get`, `@index`, `@post`),
  resolved by `Spark.Dsl.Extension` at **compile time** from literal Elixir AST in the
  module body. Downstream code reads them via `Spark.Dsl.Transformer.get_entities([:json_api,
  :routes])` (`resource/transformers/validate_no_overlapping_routes.ex:11`). There is
  no `routes: [...]` runtime keyword, and no evidence anywhere in
  `resource/transformers/` or `resource/persisters/define_router.ex` of building the
  DSL from an external data structure — **only two paths exist to generate routes
  "from data": (a) template literal macro-call source text (`get :read`, `index
  :read`, ...) at generation time — the same strategy the working
  `ash-lifecycle-pack` already uses for attributes/relationships — or (b) write a
  custom `Spark.Dsl.Transformer` that programmatically constructs route entities at
  compile time, a nontrivial Spark-internals path with zero scaffolding anywhere in
  `ggen_igniter` today.**

### 2.4 The two candidate starter packs checked, and why neither fits

From `ash-extension-starter-pack-fit` research (`ash-extension-core-pack`,
`ash-extension-starter-pack`): both packs generate **brand-new Spark DSL extensions**
(the `ash_r2rml`-style manufacturing pattern: `aex:AshExtensionSpec` → a new `use
Spark.Dsl.Extension` module). Neither has:

- An ontology class for an AshJsonApi route entry (verb, path, action, primary key).
- A template emitting a `json_api do routes do ... end end` block for a
  **caller-named existing resource**.
- A template emitting an `AshJsonApi.Router` module or a `forward "/api", to:
  SomeApp.AshJsonApi.Router` line for a caller-named existing domain.

The only place either pack touches `AshJsonApi` at all is a test-fixture composition
check (`ash-extension-core-pack/templates/composition_test.exs.tmpl`) that asserts
`ash_json_api`'s `Info` module exposes `type/1` — a presence check, not code
generation — and this incompleteness is self-disclosed in that pack's own
`pack.toml:47-52`. Both packs presuppose the target module doesn't exist yet
(`aex:AshExtensionSpec` models "one extension to manufacture from scratch"); neither
has a notion of "add JSON:API exposure to an already-defined resource/domain."

**Conclusion carried into this plan:** there is no reusable existing pack to point
`beam4pm-process-model-pack` at. New ontology vocabulary and new templates, scoped
inside `beam4pm-process-model-pack` (or a new sibling pack, see §3.1), are required.

## 3. Target design

### 3.1 Ontology admission-fact vocabulary (extends the real `bpm:` pattern)

Following the existing pattern where `bpm:RecordType` individuals (admitted facts in
`ontology.ttl`) drive `beam4pm_ash_resource.ex.eex` and `beam4pm_ash_domain.ex.eex`,
add a parallel admission-fact class for JSON:API exposure. This must live in
beam4pm's own `ontology.ttl` (the consumer ontology, per the existing
`records.rq`/`ash_fields.rq` split between consumer facts and pack vocabulary):

```turtle
# New classes/properties, beam4pm's ontology.ttl (consumer side)
bpm:JsonApiExposure a rdfs:Class .
bpm:exposesRecordType a rdf:Property ;
    rdfs:domain bpm:JsonApiExposure ;
    rdfs:range bpm:RecordType .
bpm:jsonApiType a rdf:Property .        # the "type" string in json_api's `type "..."`
bpm:jsonApiRoutePrimaryKey a rdf:Property .

bpm:JsonApiRoute a rdfs:Class .
bpm:routeVerb a rdf:Property .          # "get" | "index" | "post" | "patch" | "delete" | "related" | "relationship"
bpm:routePath a rdf:Property .          # e.g. "/:id"
bpm:routeAction a rdf:Property .        # the Ash action name, e.g. :read, :create
bpm:belongsToExposure a rdf:Property ;
    rdfs:domain bpm:JsonApiRoute ;
    rdfs:range bpm:JsonApiExposure .

# Domain-level router mount admission fact
bpm:JsonApiRouterMount a rdfs:Class .
bpm:mountPath a rdf:Property .          # e.g. "/api/json"
bpm:mountsDomain a rdf:Property .       # -> the domain module
```

This is new vocabulary — the `ash-extension-starter-pack-fit` research confirmed
**no existing ontology anywhere in the ecosystem** (neither `ash-extension-core-pack`
nor `ash-extension-starter-pack`) has route/router vocabulary. It must be authored as
part of this plan's first Develop-phase step, not assumed present.

### 3.2 Generation strategy: whole-file/whole-block EEx templating — not AST injection

The research is unambiguous on this: `ggen_igniter` has **no AST-level DSL-injection
precedent** for Ash resources of any kind (§2.3), and `ash_json_api`'s DSL is
compile-time-macro-based with no data-driven escape hatch (§2.3, `resource/
transformers/`). The only viable option the evidence supports is **(a) whole-file EEx
generation, extending beam4pm's own already-generated resource files** — not "real
Igniter-based DSL injection into an existing hand-written resource," because that
capability does not exist in `ggen_igniter` today for any Ash DSL section, and the one
Ash pack that does exist (`ash-lifecycle-pack`) uses the whole-file strategy
specifically because injection isn't available.

Concretely, since `lib/beam4pm_ash/resources/<record_name>.ex` is **already**
ggen_igniter-generated (per `beam4pm_ash_resource.ex.eex`, stage 1a in §2.1), the
correct integration point is to **extend that same template** to conditionally emit a
`json_api do ... end` block inside the already-generated resource module, driven by
the new `bpm:JsonApiExposure`/`bpm:JsonApiRoute` facts joined against the
resource's own `bpm:RecordType` identity — not a second, separate injection pass into
a file this pipeline doesn't own. This keeps the resource file's ownership single
(`# GENERATED by ggen_igniter ... Do not edit.` stays true for the whole file) and
avoids inventing an injection mechanism the tooling doesn't have.

A new query, `ash_json_api_routes.rq`, joins `bpm:JsonApiRoute` rows to their
resource via `bpm:belongsToExposure`/`bpm:exposesRecordType`, analogous to how
`ash_fields.rq` already joins `bpm:Field` rows to `bpm:RecordType`. It must be added
to the **stage 1a** `mix ggen_igniter.sync` invocation as an additional `--query`
flag, reading from the same merged ontology (`tmp_probe/ontology_merged.ttl`) if any
route vocabulary (analogous to `bpm:FieldType`'s `bpm:ashTypeExpr`) needs to live in
the pack rather than the consumer.

For the **domain-level router mount** (a new `AshJsonApi.Router` module, or a
`forward` line in `lib/beam4pm_application.ex`'s router), the equivalent stage-2-style
whole-file generation applies: a new template,
`beam4pm_ash_json_api_router.ex.eex`, driven by `bpm:JsonApiRouterMount` facts and
the same `records.rq`-derived resource list already used by
`beam4pm_ash_domain.ex.eex`, emits a new generated file, e.g.
`lib/beam4pm_ash/json_api_router.ex`. `lib/beam4pm_application.ex`'s supervision tree
would then need one hand-authored line mounting that router in the Phoenix/Plug
pipeline — this one line is **not** ggen_igniter-generated (per §2.3, `application.ex`
supervision-tree patching is the one place `ggen_igniter` does real AST-level
injection, via `Igniter.Code.Function.move_to_defp` on `Supervisor.start_link`
children — this existing, real capability, not a new one, is what would wire the
router's supervision entry, if beam4pm uses a Plug/Phoenix endpoint under
supervision; if instead it's a plain `forward` in an existing Phoenix router module,
that edit is manual, one-line, and out of ggen_igniter's generation scope entirely).

### 3.3 Why this is the option the research supports, stated plainly

- Structured/AST DSL injection into an *existing, independently-authored* resource:
  **not supported** by `ggen_igniter` today (§2.3) — ruled out.
- A brand-new Spark extension pack (`ash-extension-core-pack` pattern) targeting
  `ash_json_api`: **not what's needed** — `ash_json_api` is an existing shipped
  extension, not a new one to manufacture; those packs' entire generation target is
  the wrong shape (§2.4) — ruled out.
- Whole-file EEx regeneration of the *already ggen_igniter-owned* resource/domain
  files, extended with new queries/templates for the new ontology facts: **the one
  precedented, working pattern** (`ash-lifecycle-pack`'s documented strategy, and
  beam4pm's own existing stage 1a/2 pipeline) — **selected**.

## 4. OpenAPI emission

`ash_json_api` is already present in `mix.lock` (`1.7.1`) with its own dependency
`open_api_spex` (`3.22.4`) — both real, resolved, unused (§2.2). Per `ash_json_api`'s
published (non-beam4pm-specific, package-level) design, once one or more resources
declare real `json_api do ... end` blocks and a domain declares `json_api do routes
do ... end end` aggregating them, `ash_json_api` exposes a real OpenAPI 3 document via
its own `AshJsonApi.OpenApi` module and a router-level Plug route (conventionally
mounted as `/open_api` alongside the JSON:API routes, using
`open_api_spex`'s `OpenApiSpex.Plug.SwaggerUI`/document-serving machinery that
`ash_json_api` wires internally). Concretely, this plan's stage-2-style router
template (`beam4pm_ash_json_api_router.ex.eex`, §3.2) must include the
`AshJsonApi.Router`'s `open_api: true` — or explicit `router.ex`'s equivalent
knob per the version pinned in `mix.lock` — plus a mounted OpenAPI-document route
under the same forward path, so `GET <mount_path>/open_api` serves the real generated
spec once routes exist. **This capability is real and shipped inside `ash_json_api`
1.7.1 itself** (the dependency beam4pm already has resolved); it is not something
`ggen_igniter` needs to build — `ggen_igniter`'s job stops at emitting the
`json_api do ... end` blocks and the router module that turns `open_api` on;
`ash_json_api`/`open_api_spex` do the actual spec generation and serving at runtime.
No research pass this session directly inspected `ash_json_api` 1.7.1's exact
`Router` module surface for the `open_api:` option name/shape — **this is an open
verification item for the Develop phase** (read the real, already-vendored
`ash_json_api` source under `beam4pm/deps/ash_json_api/lib/ash_json_api/router.ex`
once beam4pm edits are authorized, rather than assumed here).

## 6. Risks / open questions

- **`ash_json_api` 1.7.1's exact OpenAPI-enablement DSL surface is unverified this
  session** — no research pass read `deps/ash_json_api/lib/ash_json_api/router.ex`
  or `open_api.ex` directly; §4's `open_api: true`-style knob is a plausible,
  version-generation-consistent description of `ash_json_api`'s public design, not a
  line-cited fact from this session's evidence. Flagged as UNVERIFIED, to be closed
  in the Develop phase against real vendored source, per this repo's own
  no-overclaiming discipline.
- **Merged-ontology mechanics** (`tmp_probe/ontology_merged.ttl`, §2.1) are a
  workaround for `ggen_igniter`'s single-`--ontology`-file limitation, not a
  first-class feature — any new pack-side vocabulary (e.g. a `bpm:RouteVerbType`
  enum analogous to `bpm:FieldType`) must go through the same merge step, and that
  merge step itself is invoked manually in the existing pipeline (not CI-gated),
  per `ecosystem-inventory-for-2030-loop`'s §4 finding.
- **The whole-file regeneration strategy (§3.2) means any hand-edit risk to
  `beam4pm_ash/resources/*.ex` remains what it already is today** — these files are
  already marked `Do not edit` and already whole-file-regenerated; this plan does not
  change that risk profile, it extends what the same regeneration renders.
- **No precedent exists anywhere in the ecosystem (ggen_igniter, either
  ash-extension pack) for AST-level injection into an existing, independently
  authored (non-generated) Ash resource.** If a future requirement needs JSON:API
  exposure added to a resource beam4pm does *not* already generate end-to-end via
  ggen_igniter, this plan's approach does not cover that case — it would require the
  heavier custom-`Spark.Dsl.Transformer` path named as unscaffolded in §2.3, which is
  out of scope here.
- **Dual-engine (Rust `ggen` vs. `ggen_igniter`) agreement** for any new
  JSON:API-related generated content is not addressed by this plan — if the Rust
  `ggen` pipeline is also expected to produce equivalent Elixir/Erlang/Gleam
  artifacts for JSON:API exposure (mirroring its existing role for `src/`/`lib/`),
  that is a separate, unscoped question this plan does not answer.
